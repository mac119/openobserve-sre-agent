# O2 Assistant — Storage Backend (design)

Status: **Phase 1 implemented** (backend extracted; SQLite default; behavior
unchanged). Phase 2 (PostgreSQL backend) and Phase 3 (migration script) remain
future work. Specifies a pluggable persistence layer so the current embedded
SQLite store and an optional PostgreSQL store can coexist, selected by config —
without changing any caller.

Motivation: SQLite is ideal for the single-server / co-located deployment
(`deploy.md`), but multi-instance / HA / horizontally-scaled deployments need a
**shared** store across agent and API replicas, which a local SQLite file cannot
provide. Rather than rip out SQLite, we abstract the backend (the same pluggable
philosophy as `llm.py`'s `LLMProvider`).

Companion docs: `architecture.md` (§7 memory), `deploy.md` (scale-out note),
`memory-longterm.md` (LTM tier). Self-test target: `o2agent.storage_selftest`
(new, offline for SQLite; PG cases gated on `O2_DB_URL`).

---

## 1. Design goals

1. **Zero-change callers.** `agent.py`, `registry.py`, `server.py`, `cli.py` keep
   calling the exact same `Memory` methods. The backend is swapped underneath.
2. **Embedded stays the default.** No `O2_DB_URL` → SQLite, no new dependency, no
   server. This preserves the single-box deployment story.
3. **Opt-in Postgres.** Set `O2_DB_URL=postgresql://…` → PostgreSQL via `psycopg`
   (an *optional* dependency, imported only when selected — same pattern as
   `cryptography` for `O2_MEMORY_KEY`).
4. **One place changes.** All persistence lives in the `memory` package; nothing
   else touches SQL.

## 2. Surface to preserve (the `Memory` contract)

The 19 public methods that callers depend on today MUST keep identical signatures
and semantics:

- Sessions: `new_session(org) -> sid`, `save_context(sid, dict)`,
  `load_context(sid) -> dict`
- Messages: `append_message(sid, msg)`, `load_messages(sid) -> list[dict]`
- Tool/usage: `record_tool_result(...)`, `record_usage(...)`,
  `session_usage(sid) -> dict`
- Feedback: `record_feedback(sid, rating, note, excerpt)`
- Result offload: `store_result(...) -> ref`, `fetch_result(ref) -> dict|None`
- Scratchpad: `get_scratchpad(sid) -> dict`, `remember(sid, kind, note, key) -> dict`
- Long-term: `remember_long_term(...)`, `get_long_term(org, limit) -> list`,
  `forget_long_term(org, key) -> bool`, `purge_long_term(org, expired_only) -> int`
- Lifecycle/retention: `close()`, `purge(retention_days) -> dict`

Cross-cutting invariants that must survive a backend swap:

- **App-layer encryption** (`MemoryCipher`) stays in `Memory`, above the backend —
  the store only ever sees ciphertext for sensitive columns. Backend-agnostic.
- **Redaction on write** (long-term) stays in `Memory`.
- **Org isolation** (long-term) stays in the SQL/params, identical on both.

## 3. Architecture

```
callers ── Memory (crypto + redaction + retention orchestration)
                │  delegates SQL to →
                ▼
        StorageBackend (abstract)
        ├── SqliteBackend   (default; stdlib sqlite3; per-thread connections)
        └── PostgresBackend (opt-in; psycopg + psycopg_pool; connection pool)
```

- `Memory` keeps its current responsibilities (encrypt/decrypt, redact, compose
  the retention purge) and delegates raw execution to a `StorageBackend`.
- The backend owns: connection lifecycle, the SQL dialect (placeholders, DDL),
  transaction handling, and concurrency (thread-local vs. pool).

### 3.1 Backend interface (thin, execution-only)

```python
class StorageBackend(Protocol):
    def init_schema(self) -> None: ...
    def execute(self, sql: str, params: tuple = ()) -> int:      # returns rowcount
        ...
    def query_one(self, sql: str, params: tuple = ()) -> dict | None: ...
    def query_all(self, sql: str, params: tuple = ()) -> list[dict]: ...
    def close(self) -> None: ...
    # dialect helpers
    @property
    def paramstyle(self) -> str: ...   # "qmark" (?) | "format" (%s)
    def ddl(self) -> list[str]: ...    # dialect-specific CREATE TABLE statements
```

`Memory` writes SQL using a neutral placeholder and lets the backend translate,
OR (simpler, chosen) each backend supplies its own DDL and `Memory` uses a tiny
`ph()` helper to emit `?` vs `%s`. Rows always come back as `dict` (SQLite via
`sqlite3.Row`→dict; PG via `psycopg.rows.dict_row`).

## 4. Dialect differences to handle

| Concern | SQLite | PostgreSQL |
|---|---|---|
| Placeholder | `?` | `%s` |
| Auto id | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| Upsert | `ON CONFLICT(col) DO UPDATE SET x=excluded.x` | **identical** (portable) |
| Row access | `sqlite3.Row` | `psycopg.rows.dict_row` |
| Concurrency | single-writer lock; `PRAGMA busy_timeout` | MVCC; no pragma; use a pool |
| Connections | thread-local (thread-affinity) | `psycopg_pool.ConnectionPool` |
| Transactions | execute + `commit()` | tx opens implicitly; **must `rollback()` on error** or the tx aborts |
| Timestamps | INTEGER epoch | BIGINT epoch (keep epoch ints; do NOT switch to `timestamptz` in v1) |
| Path/DSN | file path | connection string (`O2_DB_URL`) |

Types map cleanly: `TEXT→TEXT`, `INTEGER→BIGINT`, `REAL→DOUBLE PRECISION`.

## 5. Transaction & concurrency policy

- **SQLite backend:** unchanged — per-thread connection, `busy_timeout=5000`,
  `commit()` per write. (Keeps the Phase-12 `ThreadingHTTPServer` fix.)
- **Postgres backend:** a `ConnectionPool`; each `execute`/`query_*` borrows a
  connection, runs in an autocommit-style unit, and on exception issues
  `rollback()` before returning the connection. This prevents one failed statement
  from poisoning subsequent requests (the key PG footgun). Pool size via
  `O2_DB_POOL_MAX` (default 8).
- Multi-instance is now safe: several agent/API replicas share one PG; upserts +
  row-level locking replace SQLite's single-writer bottleneck.

## 6. Config

| Key | Default | Meaning |
|---|---|---|
| `O2_DB_URL` | *(empty)* | empty → SQLite; `postgresql://user:pw@host/db` → Postgres |
| `O2_DB_PATH` | `~/.o2agent/memory.db` | SQLite file (unchanged) |
| `O2_DB_POOL_MAX` | `8` | Postgres connection-pool size |

`requirements.txt`: add `psycopg[binary]>=3.1` and `psycopg_pool` as **optional**
(documented as needed only when `O2_DB_URL` is Postgres), mirroring how
`cryptography` is optional for memory encryption.

## 7. Migration (SQLite → Postgres)

- New deployments: just set `O2_DB_URL`; `init_schema()` creates tables.
- Existing data: a small `o2agent.migrate_store` script reads all rows via the
  SQLite backend and writes them through the Postgres backend (ciphertext copied
  verbatim — no re-encryption needed, since encryption is app-layer and the key is
  unchanged). Idempotent; safe to re-run (upserts by primary key).

## 8. Test plan

- `storage_selftest` (offline): run the full `Memory` contract against the SQLite
  backend in a temp file — every method round-trips; retention purge cascades;
  LTM upsert/evict/expire; encryption still transparent.
- Postgres cases: same suite, gated on `O2_DB_URL` being set (skipped otherwise),
  so CI stays offline by default. Asserts the PG footguns are handled: a failing
  statement does not poison the next query (rollback path), and concurrent writers
  from multiple threads all succeed.
- Regression: existing `ctx_selftest` / `sec_selftest` / `ux_selftest` /
  `server_selftest` must stay green with the default (SQLite) backend.

## 9. Phasing

- **Phase 1:** extract `StorageBackend` + `SqliteBackend`; `Memory` delegates;
  behavior identical; `storage_selftest` added. (No PG yet — pure refactor,
  de-risks everything.)
- **Phase 2:** add `PostgresBackend` (psycopg + pool + rollback discipline) behind
  `O2_DB_URL`; gated PG self-tests; `deploy.md` gains a "shared Postgres for
  multi-instance" topology.
- **Phase 3:** `migrate_store` script + docs.

## 10. Out of scope (v1)

- ORM / query builder — the SQL is small and hand-written; an ORM would add weight
  for little gain.
- Switching timestamps to `timestamptz`, JSONB columns, or PG full-text — keep the
  schema portable and minimal first.
- Other backends (MySQL, cloud KV). The interface allows them later.

## 11. Risks & mitigations

- **Transaction poisoning (PG):** the single biggest behavioral risk; mitigated by
  the rollback-on-error policy in the backend and a dedicated self-test.
- **Optional-dependency drift:** importing `psycopg` only when selected keeps the
  default install stdlib-only; a clear startup error if `O2_DB_URL` is Postgres but
  the driver is missing (mirrors `CryptoUnavailable`).
- **Refactor risk:** Phase 1 is a behavior-preserving extraction verified by the
  full existing suite before any PG code lands.
